四个独立 skill，横版和俯视人形角色分别实现：

| Skill | 内容 |
|---|---|
| `game-sprite-animator` | 横版 RPG 动作，27 个动作，5 个角色模板，高清和像素两种风格 |
| `game-shooter-animator` | 横版射击，6 种枪、9 个瞄准方向，上下半身分层，4 个角色模板 |

## 2. 对 2.0 技术方案的评审结论

方案原稿在 `docs/plans/`。优化它的时候请对照下面几点，并以仓库的实际代码为准。

**保留：**
- 先审计再动手、分阶段、向后兼容
- 导出分验证等级，生成文件不等于验证过（已写进 `CLAUDE.md`）
- 不准靠放宽阈值通过质检，未实现的检查要标明
- 故障注入测试（已实现，见 `dev/tests/test_qa_faults.py`）
- 俯视角不能旋转侧视图；2D 重叠不等于穿模；分层素材优先

**和仓库实际情况不符，需要改：**
- 方案没提 `game-shooter-animator`，两个 skill 都要考虑
- 方案把很多已有功能写成新功能：运动质检、约束、穿模检测、视觉质检、分层 PNG、各引擎导出、分层动作加烘焙组合（已经是离线的混合）
- 方案的目录结构（约 60 个文件、`pyproject.toml`、`python -m` 命令行、JSON Schema v1→v2 转换）会打破 skill 的安装方式：skill 必须是一个能直接复制的文件夹，用户不会 `pip install`
- Phase 0 审计文档（`audit.md`、`current-architecture.md`）已由 `HANDOVER.md`、`CLAUDE.md` 和本文档覆盖

**范围过大，建议删掉或推迟：**
- 8 类骨骼一起推进。先做俯视人形，再做四足，其他按需求再说
- 状态机、Blend Tree、过渡规则：这些是游戏引擎运行时的事，本工具离线烘焙序列帧
- 网格变形、时间轴编辑器
- 动作改成纯 JSON 关键帧：现有动作是 Python 程序算出来的（`Gait`、`Proc`），改成纯数据会失去这个能力。可以只给自定义动作开 JSON 入口

**方案低估的部分：**
- **绘制才是大头。** 角色外观来自 `art.py` 里 780 行专门画侧视人形的代码。每加一种角色类型或一个视角，都要重写一套画法，这决定画面质量和大部分工作量
- **统一 Rig 接口不要先设计。** 先把第二种骨骼写出来，再从两个真实例子里提炼共同接口

**2026-10-31 更新：** 人形和四足两个真实例子都已写出，现在进入提炼阶段（第 3.4 节）。方案 4.8 节"用 JSON 定义自定义骨骼"的思路因此被采纳，但按运动方式组织动作，而不是方案里的八类骨骼家族各写一套。外观改为 AI 生图（第 3 节），这一点方案原稿没有覆盖。

## 3. 新方向：AI 出图 + 配置驱动的生物

### 3.0 为什么调整

按原来的做法，每种生物都要写三样代码：骨骼、动作、画法。人形、射击、俯视、四足已经是四个独立的 skill，加飞行生物还要再写第五个，鸟、蝙蝠、龙、飞虫还得各写一遍。物种无穷无尽，这样写不完。

而且画面效果大约七成取决于画，三成取决于动。动是这个项目的强项：骨骼、平滑曲线、脚不打滑、循环无缝、自动质检、引擎实测。画是短板：用椭圆、胶囊、色块程序绘制，Q 版人形还行，龙、飞虫这类复杂外形到不了"效果好"。

新方向：
1. **画和动分开。** 外观用 AI 生图工具出图，拆成分层 PNG 部件；我们负责绑骨、生成动作、质检、导出。程序绘制保留，用来快速出原型、做占位
2. **按运动方式写代码，物种写成配置。** 扇翅、腿的步态、身体波动、通用受击和死亡各写一次。鸟、蝙蝠、龙、飞虫只是配置，区别在翅膀节数、扇动频率、幅度和身体重量
3. **合并成一个 skill。** 一份角色描述可以用在横版和俯视两种模式里，公共代码只存一份
4. **先过质量关，再扩种类。** 每个阶段都要用户看过效果、认可后再往下做

用户已确认：
- 外观来源：AI 生图工具
- 游戏横版、俯视都有，也需要怪物和飞行生物

**要接受的限制，做之前要和用户说清楚：**
- Claude 本身不能生成图片。流程是：Claude 写好生图提示词，用户在自己的工具里出图，把图片放进文件夹，skill 接着处理。以后可以接入生图 API（需要用户提供密钥），见 3.6
- 把一整张图自动拆成部件，做不到完全可靠。由 Claude 看图标出关节点、工具按骨骼切块，再由用户在预览里修正，每个角色预计人工 10～20 分钟
- 被挡住的部分（比如身体后面的远侧手臂）在原图里看不见，需要单独生成或补画
- 骨骼动画看起来是"关节纸片人"的风格（类似 Spine 做的游戏），到不了逐帧手绘像素动画的水准

### 3.2 阶段 A：验证 AI 美术流程（风险最大，最先做）

先用**现有的横版人形骨骼**验证"AI 出图 → 拆部件 → 动起来"这条路，不写任何新骨骼。现有 `Cutout`（`art.py`）已经支持把分层 PNG 绑到骨骼上，27 个动作、布料、质检、导出都能用，但**从来没有过样例和测试**，要先补上。

步骤：
1. **生图提示词模板**（`references/ai-art.md`）：按身体类型给出提示词。要求包括：侧面朝右；四肢略微离开身体，减少遮挡；纯色或透明背景；光照均匀，不要强烈投影；全身不裁切；同一角色的多张图保持一致的风格描述。还要写清楚每种常见生图工具怎么设置透明背景
2. **关节模板图**：从骨骼的静止姿势生成一张参考图，标出每个关节点应该在的位置，给用户和 Claude 对照
3. **拆部件工具**（`scripts/cut_parts.py`）：
   - 输入：全身图，加一份关节点坐标（Claude 看图提出，用户可改）
   - 按骨骼切成部件，关节处留圆形重叠，弯曲时不露缝
   - 自动去背景（透明背景优先；纯色背景按颜色抠）
   - 输出：部件 PNG 和 `parts` 配置，`pivot` 自动算好
   - 报告看不见、需要补画的区域，比如远侧手臂被身体挡住
4. **远侧肢体**：先试"复用近侧肢体并压暗"，这是现有程序绘制的做法（`darken_far`）；效果不够再要求单独生成
5. **绑定预览**（`scripts/bind_preview.py`）：静止姿势加骨骼叠加图，再加几个测试动作（走、跑、攻击、受击）的审查图，让用户几分钟内看出切错的地方
6. **静止姿势要求**：现有 `Cutout` 要求部件按"四肢自然下垂、躯干直立、武器朝上、脚平放朝右"来画。AI 出的图不会正好是这个姿势，所以切块时要按图里实际的骨骼角度记录每个部件的静止角度，绑定时补偿回去
7. **像素风**：从高清部件缩小，再按调色板量化，看效果是否可用

验收：
- 用 AI 生图做 2 个角色（比如骑士和法师），跑完 27 个动作：全量质检 0 FAIL，视觉质检没有 bug 级问题
- 关节处弯曲不露缝，远侧肢体看起来合理
- Cutout 模式加入回归基准和引擎实测
- **质量关：用户拿去和自己喜欢的游戏对比，认可后才进入下一阶段。** 不认可就继续调，不往下铺

**进度（2026-10-31）：不依赖用户选择的部分已完成，等用户的第一张 AI 图。**
- `scripts/cut_parts.py`：`template` 出参考姿势和关节表；`cut` 按骨骼切块（几何优先、颜色差别明显时改判；被挡住的地方用部件自己的颜色补；四肢关节端补成圆头；自动去纯色背景）；按标点测量骨长，并让骨骼的肩、髋、头的挂点对齐标点；`check` 让切好的角色跑 8 个最吃关节的动作，出动作预览图，报告哪个关节在哪个动作里裂缝
- 标注检查：关节在图外或不在角色身上、远近两侧长度对不上、脚的长度不对
- 自测：把程序画的 hero 渲染成一整张图再切开，和原版逐帧比较，轮廓平均重合 0.944；关节点随机偏 6 像素（约身高 2.4%）以内不裂缝，偏 9 像素会裂缝，同时报出警告和裂缝位置
- `Cutout` 的武器改为挂在拳头处（手腕往前，沿前臂），和程序画法、地面约束用同一个点；程序画法逐像素不变
- 示例角色 `assets/characters/cutout_demo/`，加入全量回归；高清版 `idle_look` 有 1 个 hold WARN（切出来的头没有表情变化），如实保留
- 文档：`references/ai-art.md`（提示词模板、标关节、切块和检查、局限）；更正了 `character-spec.md` 里"剪纸模式会画布料"的错误说法
- 测试：`dev/tests/test_cutout.py`（往返相似度、纯色背景、标点误差、标注故障、只有动作检查能发现的故障、示例与工具一致、示例通过质检）；`dev/cutout_match.py` 测相似度
- 发现的局限，留作后续：切出来的头没有表情（可以让 AI 多出几张头部表情图）；剪纸模式不画布料；Claude 目测标点需要"画出来看再修正"

### 3.3 阶段 B：合并成一个 skill

把四个 skill 合并成一个（名字待定，比如 `game-animator`）。

### 3.4 阶段 C：配置驱动的身体和按运动方式写的动作库

**身体用配置描述**（JSON）：骨头列表（父骨、长度、静止角度）、标签（腿、翅膀、尾巴、脊柱、手臂、头）、关节限位、每块骨头对应的部件（PNG，或程序绘制的形状作为占位）、前后层级、镜像规则。

**动作按运动方式写一次：**

| 运动方式 | 适用 | 主要参数 |
|---|---|---|
| 扇翅 | 鸟、蝙蝠、龙、飞虫、飞行机器 | 翅膀节数、扇动频率、幅度、下拍和上拍的时间比、收翅时机、身体起伏和扇翅的同步 |
| 腿的步态 | 任意条腿：2、4、6、8 | 每条腿的相位表、支撑占比、步幅（从现有四足的狼提炼） |
| 身体波动 | 蛇、尾巴、触手、鱼 | 波长、波速、振幅、从头到尾的衰减 |
| 通用 | 所有生物 | 呼吸待机、受击后仰、死亡倒地或坠落 |

- 动作参考真实动物的运动规律（鸟和蝙蝠的扇翅周期、四足步态的相位关系），加上跟随、甩尾这类次级运动（复用 `cloth.py`）
- 横版人形的 27 个手调动作保留，作为最精细的一类，不强行套进通用系统
- 现有的狼改用配置描述，验证四足能套进来，输出和原版对比后再决定是否替换

**质检按运动方式扩展：**
- 扇翅：左右翅相位一致、翅尖轨迹连续、身体起伏和扇翅同步、循环无缝；空中动作不做脚步滑动检查
- 步态：任意条腿的落脚滑动和悬空检查
- 波动：链条连续、不打结、不穿过自己
- 每项新检查都要配故障注入测试

验收：
- 只用配置和 AI 生图的部件做出**鸟、蝙蝠、龙**三种，动作包括扇翅、滑翔、悬停、俯冲、受击、坠落，不为单个物种写专门代码
- 全量质检 0 FAIL，引擎实测通过
- **质量关：用户认可后再加其他生物**（飞虫、蛇、蜘蛛、史莱姆、机甲等），每种只需要写配置

## 4. 已完成的工作（方向调整前）

### 4.1 补上两个质检缺口（已实现）

此前故障注入测试发现两类问题查不出来，写成了 `expectedFailure`（`dev/tests/test_qa_faults.py`）：

1. **截短的步态循环。** 走路每帧本来就改变大半剪影，像素接缝比例总在 1.7 以下，删掉 13 帧里的 1～6 帧都能通过
2. **衔接姿势错误。** 衔接比例除以较快动作的典型步长，像素差又会饱和。把死亡最后一帧接到起跳，比例只有约 1.5，阈值是 2.5

做法：在 `qa_motion.py` 里加基于关节位置的检查，数据来自 `rig_trace.json` 的 `joints`（`generate.py` 的 `TRACE_JOINTS`）。
- 接缝：最后一帧到第一帧的关节位移，和动作内平均每帧关节位移比较
- 衔接：A 最后一帧和 B 第一帧的关节位移，用身高归一化，不除以动作速度

验收：
- 两个 `expectedFailure` 测试变成普通测试并通过
- 全量回归仍然 0 FAIL。如果冒出新的 FAIL，先确认是真问题还是误判；真问题就修动作，不调阈值
- 两个 skill 都要改（`qa_motion.py` 两边不同，不在 `shared/`）

本轮实现：两边保留像素检查，并合入关节 RMS 位移检查；射击生成器补上原先没有的
`joints` 数据。故障测试改为同步修改 PNG、manifest 和 trace，并覆盖两种 skill、
纯关节故障、缩放不变性、旧 trace 兼容和开火边界。开火瞬间用绝对姿势位移限值，
整身射击组合仍检查下半身步态，规则见 `references/motion-qa.md`。

随后发现并修复了 `block_hit -> block` 的姿势跳变：保留原有格挡入场段，受击恢复时通过
`next_frame` 接回最后的 GUARD 保持帧。布料收尾、QA 和试玩控制器使用同一个目标。
试玩覆盖连续受击、释放按键和格挡火花；QA 故障测试证明重播入场和破坏目标姿势仍会报告。
另有 FPS override 用例验证入口帧号由实际输出帧数计算，不写死。

验收完成：46 项测试全部通过；18 套、864 个动作全量回归 0 FAIL、0 WARN。
10 套普通角色的试玩恢复断言通过。更新基准前已确认只有 10 个 `block_hit` 的布料像素变化，
其余 854 个动作帧数和像素不变。人工查看格挡帧后更新了基准，随后严格比较无回退、无变化。

实现：
