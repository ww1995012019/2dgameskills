## 1. 现状

四个独立 skill，横版和俯视人形角色分别实现：

| Skill | 内容 |
|---|---|
| `game-sprite-animator` | 横版 RPG 动作，27 个动作，5 个角色模板，高清和像素两种风格 |
| `game-shooter-animator` | 横版射击，6 种枪、9 个瞄准方向，上下半身分层，4 个角色模板 |
| `game-topdown-animator` | 3/4 俯视、自由移动、八方向，6 种动作 × 8 朝向，2 个角色模板 |
| `game-quadruped-animator` | 侧视狼，idle/walk/trot/run，四条三段腿与模拟尾巴 |

运行时只依赖 Python、`pillow` 和 `numpy`。每个 skill 是独立文件夹，复制或打包成 `.skill` 就能装。

已具备：
- 骨骼和软约束（`rig.py`、`constraints.py`）、布料模拟（`cloth.py`）、程序化绘制（`art.py`）、分层 PNG 绑定（`Cutout`）
- 数值质检：重复帧、循环接缝、跳帧、滑步、脚抖、衔接、关节限位、穿模、出画、握枪、射击节奏（`qa_motion.py`）
- AI 视觉质检流程（`visual_review.py`）
- 导出：序列帧、精灵图、图集、`animations.json`、Godot、Cocos、Unity、Phaser、PixiJS、CSS、Canvas 播放器

工程基础（第四、五轮）：
- 共用代码只有一份（`shared/` + `dev/sync_shared.py`）
- 18 套全量回归基准（`dev/baseline.json`），重构可以证明逐像素不变
- 故障注入测试，覆盖每一项质检
- 实测验证：Godot 4.3、Phaser 3.80、PixiJS 8.6、Chromium CSS 都做了导入和播放测试，18 套全部逐帧和原图一致

验证程度（详见各 skill 的 `references/*integration.md`）：

| 导出 | 程度 |
|---|---|
| `atlas.png`、`animations.json`、`sprite-player.js` | 实际播放 |
| `atlas.json`（Phaser、PixiJS） | 实际导入和播放 |
| Godot `.tres` + `.import` | 实际导入和播放 |
| `sprites.css` | Chromium 里实际播放 |
| Cocos `.plist` | 只做了结构校验 |
| Unity `SpriteSetImporter.cs` | 从未编译运行 |

## 2. 对 2.0 技术方案的评审结论

方案原稿在 `docs/plans/`。优化它的时候请对照下面几点，并以仓库的实际代码为准。

**保留：**
- 先审计再动手、分阶段、向后兼容
- 导出分验证等级，生成文件不等于验证过（已写进 `CLAUDE.md`）
- 不准靠放宽阈值通过质检，未实现的检查要标明
- 故障注入测试（已实现，见 `dev/tests/test_qa_faults.py`）
- 俯视角不能旋转侧视图；2D 重叠不等于穿模；分层素材优先

**和仓库实际情况不符，需要改：**
- 方案没提 `game-shooter-animator`，两个 skill 都要考虑
- 方案把很多已有功能写成新功能：运动质检、约束、穿模检测、视觉质检、分层 PNG、各引擎导出、分层动作加烘焙组合（已经是离线的混合）
- 方案的目录结构（约 60 个文件、`pyproject.toml`、`python -m` 命令行、JSON Schema v1→v2 转换）会打破 skill 的安装方式：skill 必须是一个能直接复制的文件夹，用户不会 `pip install`
- Phase 0 审计文档（`audit.md`、`current-architecture.md`）已由 `HANDOVER.md`、`CLAUDE.md` 和本文档覆盖

**范围过大，建议删掉或推迟：**
- 8 类骨骼一起推进。先做俯视人形，再做四足，其他按需求再说
- 状态机、Blend Tree、过渡规则：这些是游戏引擎运行时的事，本工具离线烘焙序列帧
- 网格变形、时间轴编辑器
- 动作改成纯 JSON 关键帧：现有动作是 Python 程序算出来的（`Gait`、`Proc`），改成纯数据会失去这个能力。可以只给自定义动作开 JSON 入口

**方案低估的部分：**
- **绘制才是大头。** 角色外观来自 `art.py` 里 780 行专门画侧视人形的代码。每加一种角色类型或一个视角，都要重写一套画法，这决定画面质量和大部分工作量
- **统一 Rig 接口不要先设计。** 先把第二种骨骼写出来，再从两个真实例子里提炼共同接口

## 3. 接下来要做的事

### 3.1 补上两个质检缺口（已实现）

此前故障注入测试发现两类问题查不出来，写成了 `expectedFailure`（`dev/tests/test_qa_faults.py`）：

1. **截短的步态循环。** 走路每帧本来就改变大半剪影，像素接缝比例总在 1.7 以下，删掉 13 帧里的 1～6 帧都能通过
2. **衔接姿势错误。** 衔接比例除以较快动作的典型步长，像素差又会饱和。把死亡最后一帧接到起跳，比例只有约 1.5，阈值是 2.5

做法：在 `qa_motion.py` 里加基于关节位置的检查，数据来自 `rig_trace.json` 的 `joints`（`generate.py` 的 `TRACE_JOINTS`）。
- 接缝：最后一帧到第一帧的关节位移，和动作内平均每帧关节位移比较
- 衔接：A 最后一帧和 B 第一帧的关节位移，用身高归一化，不除以动作速度

验收：
- 两个 `expectedFailure` 测试变成普通测试并通过
- 全量回归仍然 0 FAIL。如果冒出新的 FAIL，先确认是真问题还是误判；真问题就修动作，不调阈值
- 两个 skill 都要改（`qa_motion.py` 两边不同，不在 `shared/`）

本轮实现：两边保留像素检查，并合入关节 RMS 位移检查；射击生成器补上原先没有的
`joints` 数据。故障测试改为同步修改 PNG、manifest 和 trace，并覆盖两种 skill、
纯关节故障、缩放不变性、旧 trace 兼容和开火边界。开火瞬间用绝对姿势位移限值，
整身射击组合仍检查下半身步态，规则见 `references/motion-qa.md`。

随后发现并修复了 `block_hit -> block` 的姿势跳变：保留原有格挡入场段，受击恢复时通过
`next_frame` 接回最后的 GUARD 保持帧。布料收尾、QA 和试玩控制器使用同一个目标。
试玩覆盖连续受击、释放按键和格挡火花；QA 故障测试证明重播入场和破坏目标姿势仍会报告。
另有 FPS override 用例验证入口帧号由实际输出帧数计算，不写死。

验收完成：46 项测试全部通过；18 套、864 个动作全量回归 0 FAIL、0 WARN。
10 套普通角色的试玩恢复断言通过。更新基准前已确认只有 10 个 `block_hit` 的布料像素变化，
其余 854 个动作帧数和像素不变。人工查看格挡帧后更新了基准，随后严格比较无回退、无变化。


### 3.2 俯视人形（八方向首版已实现）

用户的游戏横版、俯视都有，也需要怪物。先做俯视人形，因为能复用最多的骨骼和动作经验。

用户已选择 **自由移动、八方向**。其余按此前建议采用 3/4 俯视、独立的
`game-topdown-animator`，首批 idle、walk、run、attack、hurt、death。

实现：
- 2.5D 地面与高度骨骼，腿 18+18、臂 14+14，固定相机投影；正面、背面、侧面和斜向各有外观及深度遮挡。
- 5 个基础朝向，3 个左向在共同 pivot 上烘焙镜像，装备会换手，manifest 明确记录。
- 两个模板 wanderer、warden；每套 48 片段，高清 1248 帧、像素 632 帧。
- 斜向移动归一化，转向和走跑切换保留步态及子帧进度，不重复派发当前脚步事件。
- 朝向/帧完整性、跨方向时序/速度/事件、二维地面滑步、骨长/武器长度、循环和衔接 QA。
- 导出沿用共用 exporter，新增独立的八方向图库、键盘试玩、审查图和故障注入测试。

验证：22 套共 1056 个片段回归 0 FAIL、0 WARN；扩充基准前确认旧 18 套的像素、帧数和 QA 数值完全不变。
两角色 × 高清/像素的四套完整素材分别通过导出还原、Godot 4.3、Phaser 3.80.1、PixiJS 8.6.6
导入和播放，以及真实 Chromium 键盘试玩检查。24 张审查图已逐张查看并在本地 `review/verdict.json` 记录。
包的独立解压运行也通过；完整 62 项测试全部通过，无跳过，详见 HANDOVER.md。

### 3.3 八方向后续优化（按游戏需要）

基础八方向已完成。当前仍只做持剑人形，暂不包含：
- 固定左右手的非对称装备（目前明确采用烘焙镜像）
- 独立瞄准与移动方向、弓箭/枪械、更多攻击动作
- 自定义分层 PNG、物理布料、真正正上方的相机

这些需要按具体游戏需求排期。当前画法偏简洁卡通，轮廓中的细剑及正背死亡姿势的透视压缩仍需游戏内观感复核。
数值通过不是语义方向/画面完美的证明；帧哈希检查只证明帧与其标记的 trace 一致。

### 3.4 四足动物（侧视狼首版已实现）

新增独立 `game-quadruped-animator`，先完成 wolf 的 idle、walk、trot、run 四个循环。
分段脊柱、颈/头与四条三段腿保持固定骨长；前肘与后膝采用不同弯曲方向。走路按四个
四分之一周期依次落脚，慢跑配对对角腿，奔跑为交错后/前腿并含腾空段。

尾巴复用 `shared/cloth.py`，通过 `state_at(t)` 传递根部和身体角度，不依赖人形求解器。
从实际人形/四足数据里提炼 `JointRecorder`，只统一关节记录，不强行统一解剖与约束。
人形默认路径保留数值运算；必须用旧 22 套的严格比较证明输出不变。

验收包含：四只脚分别注入滑步、悬空、腿拉长、保持骨长的反折、错误落脚/事件、
尾巴根部脱离或穿地、循环跳变、裁切、非有限值；另测 24fps 分数模拟采样、预览控制器和独立解包运行。
高清/像素分别在 Godot、Phaser、PixiJS 以 60/144Hz 播放全部四动作，并做真实浏览器键盘试玩。
完整 79 项测试通过，无跳过；24 套、1064 片段回归 0 FAIL、0 WARN。旧 22 套逐像素、帧数、QA 数值
完全不变；扩充后的严格基准比较无回退、无变化。具体记录见 HANDOVER.md。

攻击、受击、死亡现已补齐：前探咬击用 hit_on/hit_off，受击恢复待机，伏地死亡保持终帧，训练靶按事件帧记命中。下一步按游戏需求考虑俯视四足或更多敌人行为。战斗版完整 83 项测试通过；24 套、1070 片段为 0 FAIL、0 WARN，旧 1064 片段未变。当前没有犬种/马等独立骨骼、
自定义部件 PNG 或接触约束的步态混合。造型为简洁的棱角卡通，需结合实际游戏复核风格。

### 3.6 引擎实测补全

- **射击 skill 的分层挂点：** 现在只测了逐帧画面和播放。要在 Godot 和 Phaser 里按文档把上半身放到下半身每帧的 `anchor` 上，截图和 `preview.html` 的合成结果比较
- **Unity、Cocos：** 需要装了编辑器的机器（这个 Linux 容器装不了，需要图形界面和授权）。Unity 要验证 `SpriteSetImporter.cs` 能编译、能生成 `.anim`、pivot 正确；Cocos 要验证 `.plist` 导入和 Trim 设置

### 3.7 遗留的观感问题

见 `HANDOVER.md` 的「视觉质检记录」：
- commando 等角色朝正下方瞄准时，枪和腿在剪影里叠在一起
- ghost 朝正下方瞄准狙击枪时，枪管搁在地面上
- goblin `attack_3` 起手时枪杆横过脸
- ninja 像素版 `attack_2` 第 2 帧刀光是折线
- goblin 像素版、swat 深色武器和衣服在剪影里不显眼（改角色配色即可）

### 3.8 可选的代码整理

`rig.py`、`render.py`、`motions.py`、`art.py`、`fx.py`、`qa_motion.py`、`generate.py` 两个 skill 各有一份，已经分开演化。可以逐个合进 `shared/`，每合一个都要用 `python3 dev/baseline.py --strict` 证明两边输出逐像素不变。做俯视 skill 之前合并 `render.py` 和 `qa_motion.py` 最有价值，因为第三个 skill 也要用。
